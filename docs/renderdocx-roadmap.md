# RenderDocX migration boundaries

The supplied upstream snapshot has version macros for RenderDoc 1.48 but no Git metadata. Its upstream files have been compared by Git blob ID to `v1.x` commit `5ad608809c9028da9f5c5082397cb6afe9c8dd17`; see the root README for the scope and exceptions. Capture and replay remain in the matching RenderDoc core. A separate C++ helper owns the replay lifetime and exposes a versioned process protocol to Rust, avoiding a guessed C++ ABI in Rust. The application API in `renderdoc/api/app/renderdoc_app.h` is a separate, versioned in-process capture interface.

The current workspace can launch or discover local RenderDoc targets, configure upstream capture options, launch arguments and environment modifications, connect without taking over an existing client, trigger captures and open reported local capture files. It can also show an expandable action hierarchy with optional API event rows, list and select each action's API events, navigate paged structured event parameters and buffer bytes, browse resource metadata, parent/derived links and paged static usage with event navigation, display common pipeline topology, shader/output bindings, buffers, vertex input metadata and viewports, inspect bound shader signatures and RenderDoc disassembly targets, browse GPU buffer bytes in pages, and inspect selected texture pixels, pixel history and histograms or preview and export subresources with RenderDoc's PNG mapping. Structured buffer access uses a separate structured-data worker and a complete structured capture export. Event names can be formatted from structured parameters in the background, with the supported rules and limitations described in `agent-cli.md`. The agent CLI shares those session implementations and additionally accepts queued captures. Common pipeline state is taken from the upstream `PipeState` implementation; OpenGL vertex input metadata is reconstructed from reflected active attributes because the upstream common implementation can contain uninitialized trailing entries. Real replay coverage exercises D3D11 and an OpenGL 3.3 capture, including selected pixel-history paths; live capture coverage includes a Unity 2022.3 D3D11 Development Player offscreen-camera capture, and a batch Editor has been connected by PID. Editor frame capture, Tuanjie, other OpenGL workflows and additional graphics APIs remain unverified. Texture export for multisample and 3D selections remains unverified; pixel and statistics coverage includes one 3D slice and a uniform D3D11 multisample fixture. `qrenderdoc` remains necessary for detailed inspection and additional workflows. There is no independent Rust `.rdc` parser or Rust implementation of the graphics replay core.

Remaining work includes:

1. Harden the version-checked replay helper, lifecycle, packaging and reproducible core builds across supported platforms.
2. Integrate target enumeration/control, launch configuration, capture progress, saved captures, remote servers, and errors using the corresponding upstream contracts.
3. Complete the event browser and port texture and mesh views, API pipeline state, resources, shader debugging, and all remaining upstream windows and workflows.
4. Integrate Unity/Tuanjie Editor and standalone workflows against the applicable documented engine APIs, graphics APIs, and versions, including capture handoff to the new frontend.
5. Extend translation resources, keyboard navigation, accessibility, settings, packaging, and platform support alongside each implemented feature.
6. Complete automated tests across protocol, UI interactions, actual captures, replay, supported GPUs, platforms, and Unity/Tuanjie before claiming parity. Compilation and mock tests alone do not establish these properties.

The agent CLI exposes RenderDoc vertex, pixel and compute shader debug trace batches, variable changes and instruction/source mappings. GPUI and the CLI can collect a trace, step through instructions or source locations, and run forward or backward to source or disassembly breakpoints. These paths have been exercised on a real D3D11 fixture, with source mapping verified for one debug-compiled compute shader. A Vulkan vertex fixture found that the matching upstream core double-applies firstVertex in non-indexed manual input fetch; the bridge conditionally compensates for the detected core implementation, and actual debugger inputs now match the selected indexed and non-indexed rows. Mutable variables are reconstructed from trace changes, and numeric source-mapping components are resolved against the current inputs and state. One real D3D11 compute trace validates input values and a calculated local across forward and reverse navigation; composite, resource and pointer value presentation remains incomplete. The desktop collects all states before display; the vertex input viewer and mesh viewer accept instance and view indices; the bridge validates views against RenderDoc multiview broadcast count for mesh and vertex debugging. Nonzero selections still need end-to-end GPU validation. Pixel debugging accepts optional primitive and view selectors; backends may ignore selectors and GPUI selector forwarding has not yet been validated with a real capture. Source step-over and step-out are implemented but require real multi-function and cross-API validation. Source expression evaluation, other stages, indirect dispatches and additional graphics APIs are still pending or unverified.

GPUI and the agent CLI can page shader-printed messages from the selected event's `PipeState::GetShaderMessages()`. Both support stage-mask and message/location text filters across all pages, plus complete filtered text or CSV export without replacing existing files. GPUI supports message links that select the target event, invocation details, copying, debug entry points for supported stages, and vertex/geometry mesh-row or pixel output-texture handoff. Vertex message coordinates resolve against the draw and its index buffer, synchronizing VS input and output; duplicate matches select the first row and disclose the count, and negative indices that the input viewer cannot represent are reported as errors. Geometry handoff follows upstream's input-topology row approximation and explicitly discloses that the instance is unknown and variable output counts can produce a different row. Debugging a message sets a breakpoint at its disassembly line or the next mapped line, runs forward and displays the actual stop; the CLI exposes the same navigation. Vulkan Task messages can locate the task output group, and direct Mesh messages can locate their meshlet. The current upstream Vulkan feedback leaves a placeholder for a Mesh message's parent task ID, so mesh messages from task-dispatched groups cannot be located or debugged reliably and are rejected; group navigation does not claim to select the original thread's output. A real D3D11 capture validates the empty result, page errors, index-buffer resolution against vertex input, and a selected disassembly-line jump on a real trace; a Vulkan mesh fixture validates Task and direct Mesh group mapping plus rejection of an unavailable parent. Vulkan captures validate Compute, Pixel, Vertex and Geometry messages; the Geometry fixture demonstrates the row approximation with variable output. A Task/Mesh printf capture exposed an upstream direct-Mesh replay crash and uninitialised Task location fields; an isolated rebuilt core and bridge pass real-message CLI, direct Mesh debugging and old-core Task sanitization checks. The GPUI interaction test using the same capture verifies Task navigation, blocks unreliable child Mesh debugging, and debugs a direct Mesh message. Full upstream shader-message behavior remains incomplete.

The frame information, replay debug messages and recorded frame statistics are available in the snapshot and have initial GPUI views. The statistics view includes an overview of actions, API calls and resource sizes, categorized per-stage metrics and histograms, complete-stage totals, raw bridge data and localized text export. Unavailable or malformed sections are not treated as zero. The overview and exported report do not yet reproduce every upstream formatting detail, and their presentation and file dialog have not been validated with a real capture in the GUI. The GUI polls for later debug messages and supports sorting, text and severity filters, hiding by source/severity/category/type, restoring hidden entries, copying and event navigation; the CLI supports explicit polling and paging. Message details resolve known resource and event references, and standalone GPU addresses can open the matching buffer at the correct byte offset; structured GPU-address parameters have the same handoff. Typed GPU pointer formatting remains unavailable and is identified as such. HTML and URL handling, full multi-cell selection and real-capture GUI validation remain outstanding. GPU counters can be selected, sampled and paged in GPUI and the agent CLI; broader driver and vendor-counter validation and the complete upstream counter workflow remain outstanding.

Pipeline color, depth and depth-resolve attachment views link to matching captured textures in GPUI. The first mip and slice are selected when valid, and the descriptor's component type is passed to PNG preview/export, picking, statistics and pixel history. Non-identity descriptor swizzles are shown in attachment and binding details. As in the checked-in upstream texture-view handoff, preview and analysis inspect the resource without applying the descriptor swizzle. A GPUI interaction test covers the handoff; a D3D11 capture test exercises the typed operations. Real capture UI interaction and non-identity swizzles from real captures remain unverified.

The initial mesh output viewer can page vertex bytes or decode 8-, 16- and 32-bit indices with base-vertex adjustment and pipeline restart markers. GUI and CLI can also page VS/GS positions in draw-index order for regular 16- and 32-bit floats, including restart and short reads, and export those positions as CSV. A D3D11 indexed capture verifies initial draw-order rows and CSV export through the CLI. The complete attribute and geometry viewers, task/mesh draw-order decoding, other APIs, restart-enabled captures, and GPU-backed draw-order UI tests remain outstanding.

The shader inspector can switch between disassembly and captured source files, displaying source in 200-line pages. The CLI's shader report exposes complete source contents, and both GUI and CLI can export a complete source file or disassembly without replacing an existing file. GUI and CLI support session-scoped compilation, shader replacement and revert through RenderDoc. Shader editor drafts can be stored in and reopened from the upstream `EditedShaders` section; loading a draft does not apply it. Multi-file source expansion follows the upstream editor's include matching, and stored compile flags can be passed to the device. A D3D11 HLSL CLI check verifies include compilation, changed pixels, revert and compile errors. The external processor CLI passes a headless type check and subprocess fixture tests; GUI configuration and real compiler execution paths have not yet been tested. External RenderDoc interoperability, broader graphics APIs and end-to-end GUI editing validation remain outstanding.

Shader reflection reports include constant block layouts, nested variables, resources and samplers in both CLI and GPUI. Both expose paged runtime bindings and resource navigation; the CLI can request a constant block array element using RenderDoc's dynamic binding and value decoder, and GPUI can step between elements. A D3D11 compute capture verifies a read/write resource, constant binding and value; GPUI fixtures test element navigation and binding-to-resource navigation. Other APIs, inline data and real capture GUI interaction remain outstanding.

Runtime binding rows display descriptor ranges and sampler parameters, and can open a matching buffer constrained to its binding range or a texture at its first mip and slice. The buffer viewer can switch back to the full resource; the CLI also supports binding-relative reads. Fixture interactions cover both links and bounded paging, while a D3D11 capture validates a bound constant-buffer read. Real capture UI and non-D3D11 binding types remain unverified.

An initial descriptor inspector pages the selected event's descriptor accesses or fixed-size stores through RenderDoc. It presents descriptor type, shader stage, binding, logical name, resource and range fields, with optional raw data for the remaining fields, and can open a bound buffer or texture. Sampler addressing, filtering, LOD, flags, border values and YCbCr parameters share a presentation with shader bindings; unsupported border types retain their raw bit patterns. Variable-sized store enumeration, complete descriptor presentation and cross-API validation remain outstanding. Sampler presentation has fixture coverage but has not been validated against real captures across graphics APIs.

Descriptor requests are grouped by store for batched upstream queries. If a driver returns an incomplete batch, the bridge retries individual ranges rather than assigning partial results to the wrong rows. A real D3D11 compute capture compares the batched page with individual requests; the incomplete-response fallback and other graphics APIs have not been exercised end to end.

Version-one capture notes and bookmarks can be read and explicitly saved through RenderDoc sections from GPUI and the agent CLI. Concurrent-writer checks are best-effort rather than an atomic lock; ordinary window-close requests are blocked for unsaved drafts and in-flight operations. Forced termination, external-editor interoperability and broader platform validation remain outstanding.

CodeGraph233 is configured for the Rust application and tests; the local index is ignored by Git. With the currently installed 0.3.1 server, C++ sources are not indexed and must still be inspected directly. Run `codegraph233 index --root . --jobs 1` to refresh the Rust graph; graph references are navigation aids and must be checked against the source.
