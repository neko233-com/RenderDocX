# Agent CLI (initial contract)

`renderdocx-cli` exposes the same native replay session used by the GPUI event browser. It does not control `qrenderdoc`. Build and configure the matching `renderdocx-replay` bridge first; `--bridge PATH` overrides the user setting for one invocation.

```text
renderdocx-cli capabilities
renderdocx-cli --bridge PATH inspect CAPTURE.rdc
renderdocx-cli --bridge PATH select CAPTURE.rdc EVENT_ID
renderdocx-cli --bridge PATH serve
```

One-shot invocations write one JSON object on stdout with `schema: "renderdocx.cli.v1"` and `ok`. Failures use a nonzero exit code and include `error.code` and `error.message`. `inspect` returns the upstream action tree flattened in depth-first order; each `parent` is the zero-based action array index or `-1` for a root. Each action's `api_events` preserves upstream order and includes its own event as well as preceding API calls. Each entry has an `event_id`, nullable `chunk_index` (null denotes upstream `NoChunk`), structured chunk `name` (empty when unavailable), and decimal-string `file_offset`, a relative stream offset rather than an on-disk file position. It also includes texture metadata; `bytes` is a decimal string to preserve the complete 64-bit value in JavaScript. The array ordering is scoped to this replay session and is not a persistent resource identifier. One-shot `select` opens its own replay session, sets an action or listed API event and returns its common pipeline state.

`serve` keeps replay and target sessions open and accepts one JSON object per stdin line. It handles requests sequentially and emits exactly one JSON response per line on stdout, using `schema: "renderdocx.agent.v1"`, echoing the optional `id`, and returning either `data` or `error.code`/`error.message`. Commands include `capabilities`, `open`, `snapshot`, `select`, `pipeline`, `shader`, `vertex_input`, `mesh`, `mesh_read`, `structure`, `read_buffer`, `resource_usage`, `pick_pixel`, `texture_statistics`, `export_texture`, `close`, the target commands below, and `quit`.

The capture `resources` array is ordered by RenderDoc's session resource list. Each entry includes its name, numeric upstream `ResourceType`, autogenerated-name flag, initialization chunk indices and `parents`/`derived` references into the same array. A null relationship means the referenced resource is absent from this list. These indices are session-scoped, not persistent resource identifiers; chunk indices refer to the structured capture, not event IDs. Older bridges may omit this array.

`resource_usage` reads RenderDoc's static usage for one resource without changing the selected replay event: `{"command":"resource_usage","index":0,"offset":"0","limit":128}`. The index refers to the capture `resources` array; offset is an unsigned decimal string, and limit defaults to 128 and must be 1–128. `total` and `offset` are decimal strings. Entries preserve upstream order and report `event_id`, numeric `ResourceUsage` and a convenience `usage_name`. `tracked: false` preserves RenderDoc's single event-0 `Unused` sentinel for resource types whose usage is not tracked; an empty tracked list instead means no static usage was observed. An event need not have a navigable action in the capture. Paging limits the IPC response; RenderDoc's underlying API returns the entire usage list for each request. Real D3D11 and OpenGL coverage includes vertex-buffer draws; D3D11 also covers an untracked shader. Other resource types and APIs need additional validation.

`structure` reads a page of direct structured-data children for any event with an available chunk, independently of the selected replay event. Use `{"command":"structure","event_id":42,"path":["0"],"offset":"0","limit":128}`. `path` is a sequence of decimal-string child indices from the chunk; it and `offset` default to the root and zero. `limit` defaults to 128 and must be 1–128. The reply contains the requested `node`, its `children`, `event_id`, `path`, and `offset`. `child_count` and `byte_size` are decimal strings, as are numeric scalar `value`s; boolean values are strings `true` or `false`, and character values are unsigned byte strings. Strings retain their UTF-8 content. `basic_type` and `flags` are upstream `SDBasic` and `SDTypeFlags` values; `custom_string` preserves upstream display metadata. Resource objects report `resource_non_null` and a session-scoped `resource_index` when available, rather than exposing the opaque `ResourceId`. Missing chunks and invalid paths return errors. This exposes structured data rather than reproducing every RenderDoc formatting rule.

`structure_buffer` reads raw bytes for an upstream `SDBasic::Buffer` node, for example `{"command":"structure_buffer","event_id":42,"path":["3"],"offset":"0","length":256}`. The response includes lowercase `hex`; offsets are decimal strings and each request is limited to 65,536 bytes. The first read opens an isolated replay worker and asks RenderDoc for the complete structured capture export, which can require substantial extra memory and time; the worker is reused for subsequent pages and closed with the session. The helper checks matching event and chunk metadata and refuses reads if file size or timestamps changed since opening. These metadata checks are not a cryptographic content-integrity guarantee. Reading structured bytes does not change the primary replay selection.

`pick_pixel` uses RenderDoc's `PickPixel` at the selected replay event, for example `{"command":"pick_pixel","index":0,"mip":1,"slice":0,"sample":0,"x":3,"y":2}`. Coordinates are in the selected mip and have a top-left origin on every API. Mip and slice default to zero; a null or omitted sample requests upstream resolve for multisampled textures and sample 0 for single-sample textures. `pixel.sample` is the actual upstream sample argument, with 4294967295 denoting resolve. The request validates coordinates and subresources. `channel`, when supplied, is validated but does not filter this RGBA result. `bits` contains the four 32-bit component patterns returned by RenderDoc; `float_values`, `uint_values` and `int_values` are alternative interpretations of those same bits, with floats encoded as strings to preserve non-finite values. They are not raw texture storage bytes. RenderDoc's API does not return an individual success status for every pixel read; supported formats and drivers determine the result. Real D3D11 tests cover mip/slice, one 3D slice, unsigned integer textures and, when supported, a uniform multisampled texture; an OpenGL test checks top-left orientation. Varying multisample values, other 3D cases, other APIs and formats still require real-capture validation.

`texture_statistics` calls RenderDoc's `GetMinMax` and `GetHistogram` for a selected event and subresource, for example `{"command":"texture_statistics","index":0,"mip":0,"slice":0,"min":0,"max":1,"channels":[true,false,false,false]}`. The range defaults to 0–1 and must remain finite, ordered and representable in float32, including its span and RenderDoc's upper-bound adjustment. `channels` is an optional four-boolean RGBA mask; when omitted it follows the selected `channel`, or all available components if no channel is selected. Minimum and maximum always cover RGBA independently of this histogram mask. The response preserves each extreme's returned 32-bit component patterns with float, unsigned and signed interpretations, plus the upstream unnormalized histogram array; an empty array means no histogram was returned. RenderDoc's public `GetMinMax` does not expose the underlying success flag and may return default values on failure, so these extrema alone do not establish success. D3D11 tests cover an array mip, one 3D slice and an unsigned integer texture; when supported, the fixture also checks a uniform multisampled texture and its resolve. OpenGL tests check histogram counts. Varying multisample values, other 3D cases and other graphics APIs still need real-capture validation.

For example:

```json
{"id":1,"command":"open","path":"C:/captures/frame.rdc"}
{"id":2,"command":"select","event_id":42}
{"id":"pipeline","command":"pipeline"}
{"id":"shader","command":"shader","stage":"vertex"}
{"id":"bytes","command":"read_buffer","index":0,"offset":"0","length":256}
{"id":3,"command":"export_texture","index":0,"path":"C:/captures/texture.png"}
{"id":"layer","command":"export_texture","index":0,"path":"C:/captures/layer.png","mip":1,"slice":0,"sample":null,"channel":0}
{"id":4,"command":"close"}
{"id":5,"command":"quit"}
```

Live control uses the matching `renderdocx-target` helper next to the configured replay bridge. `target_list` enumerates local RenderDoc target identifiers; `target_connect` takes a nonzero `ident`. `target_connect_pid` takes a nonzero `pid` and searches available local targets by process ID. Neither force-disconnects a busy client; PID lookup briefly probes other available local targets while searching. `target_launch` takes an executable `path`, an existing absolute `capture_directory`, and optional platform-specific raw `arguments`; each launch creates a fresh session subdirectory to avoid overwriting captures from earlier runs, and returns its `capture_template`. `target_trigger` takes nonzero `frames`; `target_queue` additionally takes the target `frame`; `target_cycle` changes the active window. These return `submitted` when the request is written to the helper, not when the target has captured a frame. Poll `target_events` to receive API registration, command-sent, capture, progress, child, window and disconnect notifications. A capture event's `path` is usable locally only when `local` is true. `target_close` disconnects without terminating the target; `quit` also closes the connection. Only one target session is held at a time. Remote target connections, remote capture copying, injection into an already-running process and remote workflows are not implemented.

For `target_launch`, optional `configuration` accepts `arguments`, an absolute existing `working_directory` (null uses the executable directory), `options`, and `environment`. For example:

```json
{"command":"target_launch","path":"C:/game/Player.exe","capture_directory":"C:/captures","configuration":{"arguments":"-screen-width 1280","working_directory":"C:/game","options":{"api_validation":true,"capture_callstacks":true},"environment":[{"name":"EXAMPLE_PATH","value":"C:/example","operation":"prepend","separator":"platform"}]}}
```

`capabilities.capture_options_default` exposes all 12 upstream options and defaults. `delay_for_debugger` is in seconds and `soft_memory_limit` in MB; the latter is an upstream soft target, not a hard limit. Each environment entry requires `name`, `value`, `operation` (`set`, `append`, `prepend`) and `separator` (`platform`, `semi_colon`, `colon`, `no_sep`). Entries are applied in order by RenderDoc. Unknown configuration fields are rejected. The older top-level `arguments` remains accepted when `configuration` is omitted. Environment values are sent to the RenderDocX helper through stdin and are not saved in RenderDocX settings or echoed in responses; the launched target necessarily receives them in its environment. On Windows, upstream's cross-bitness injection path may pass environment values through an additional helper's command line. Application arguments remain visible to the operating system as part of the target command line. The GUI also supports ordered environment modifications and masks the value input.

An unsuccessful `open` leaves the previous session intact. `pipeline` requires a selected event and returns RenderDoc's common topology enum, shader stages, output bindings, index and vertex buffers, vertex input metadata, and viewports. `resource_index` is the index in the upstream resource list for this session only, or null when the resource is absent from that list; it is not the texture index or a persistent identifier. Buffer `byte_offset` and `byte_size` are decimal strings preserving upstream 64-bit values, including sentinel sizes that do not represent the actual buffer length. Non-finite viewport coordinates are represented as null. `available: false` means RenderDoc did not provide a pipeline state. OpenGL vertex inputs are built from the pipeline state and shader reflection to avoid uninitialized trailing entries in the upstream common implementation; `vertex_inputs` is null when reflection is unavailable. Generic component bit patterns are exposed as `generic_bits`. New pipeline fields are null when an older bridge does not provide them. This is a subset: API-specific pipeline details, source editing, shader debugging, texture raw pixels and remote capture are not yet exposed. `export_texture` requires a selected event and writes PNG using RenderDoc's default mapping; it never replaces an existing destination. `close` and `quit` wait for the replay helper to shut down, releasing its capture file before acknowledging. The server opens no network listener and performs no authentication; only processes with access to its stdin can send commands.

`shader` inspects the shader bound at the selected event. `stage` is one of the names in `capabilities.shader_stages`; `target_index` is optional and indexes the `targets` array returned for that stage and event. Omitting it or using null asks RenderDoc for its default. The result includes entry point, encoding, signature metadata, resource counts, supported targets and the disassembly text. RenderDoc may return an error message as the disassembly text; a successful request does not establish that disassembly or decompilation succeeded. Unbound stages and missing reflection return errors.

`mesh` queries RenderDoc's generated post-shader output for the currently selected draw or mesh-dispatch action, for example `{"command":"mesh","stage":"vs_out","instance":0,"view":0}`. Stages are `vs_out`, `gs_out`, `task_out`, and `mesh_out`; instance and view default to zero. An unavailable stage may return an unbound resource or an upstream status rather than an error. Task and mesh shader stages are rejected for D3D11 and OpenGL. Nonzero views are currently rejected because replay backends may silently clamp or ignore them and this interface cannot yet verify the actual view count. The result exposes upstream format, topology, strides, index metadata, meshlets and status. Decimal-string offsets and sizes retain upstream sentinel values, which need not equal actual buffer lengths. Non-finite near/far values are null; `dispatch_size` is null when unavailable. Resource IDs are not persistent and are not exposed.

`vertex_input` reads shader input attributes in draw order for a selected draw action: `{"command":"vertex_input","instance":0,"offset":0,"limit":64}`. Instance and row offset default to zero; the limit defaults to 64 and must be 1–64. The reply includes the original and resolved indices, primitive-restart rows, and used attributes. It applies RenderDoc's buffer bindings, draw offsets, base vertex and instance rates. Available values include raw lowercase `hex`; regular float16, float32 and float64, signed and unsigned integers, scaled values, 8- and 16-bit normalized values and selected packed formats also include string `values`. Other formats retain raw bytes and null `values`; supported generic attributes return decoded values without buffer bytes. Out-of-range or unbound inputs are marked unavailable. This command needs a bridge providing draw-offset, format and primitive-restart metadata; it fails when those are absent. D3D11 indexed and OpenGL 3.3 non-indexed vertex input, including a normalized attribute and a generic float attribute, have been verified with actual captures; other APIs and formats require real-capture validation.

After a successful query, `mesh_read` reads its generated vertex or index buffer: `{"command":"mesh_read","kind":"vertex","offset":"0","length":256}`. Offsets are decimal strings relative to the returned buffer offset; length is at most 65,536 bytes, zero returns no bytes, and a short read is reported with its actual length. Changing the selected event, opening or closing a capture, or a failed mesh query invalidates the CLI mesh selection. This is raw buffer order, not reconstructed draw-index order. D3D11 VS output is covered with a real capture; other stages and APIs need real-capture validation.

The capture snapshot lists `buffers` with session-scoped indices, upstream `resource_index`, `creation_flags`, and a decimal-string `length`. `read_buffer` requires a selected event, the buffer array `index`, an unsigned decimal-string `offset`, and an integer `length`. It returns `event_id`, `index`, `offset`, and lowercase hexadecimal bytes in `hex`. The range must lie within the buffer; length zero returns an empty result even though the upstream API uses zero to mean the rest of the buffer. Each request is limited to 65,536 bytes to bound IPC response size; page through larger buffers with successive offsets. A short or failed upstream read is an error. Generic texture raw pixels remain unavailable.

`export_texture` optionally accepts unsigned `mip` and `slice` indices (both default to 0), plus `sample` and `channel` (unsigned indices or null). Null `sample` requests RenderDoc's resolve; null `channel` requests all components. `slice` selects the array layer or, for a 3D texture, the depth slice at the chosen mip. Indices are validated against the capture metadata instead of silently clamped. The response echoes the selection. PNG conversion and channel extraction follow RenderDoc's format-dependent behavior, with its default black/white mapping. The 2D array and channel paths have real D3D11 coverage; multisample and 3D paths have not been validated against real captures. An older bridge can handle the default selection but reports an error for non-default selections.

The helper and its RenderDoc core must be built from matching source revisions. `select` returning success means the upstream replay call returned without a fatal error, not that the rendered output was visually validated.
