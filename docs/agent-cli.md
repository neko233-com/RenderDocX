# Agent CLI (initial contract)

`renderdocx-cli` exposes the same native replay session used by the GPUI event browser. It does not control `qrenderdoc`. Build and configure the matching `renderdocx-replay` bridge first; `--bridge PATH` overrides the user setting for one invocation.

```text
renderdocx-cli capabilities
renderdocx-cli --bridge PATH inspect CAPTURE.rdc
renderdocx-cli --bridge PATH select CAPTURE.rdc EVENT_ID
renderdocx-cli --bridge PATH serve
```

One-shot invocations write one JSON object on stdout with `schema: "renderdocx.cli.v1"` and `ok`. Failures use a nonzero exit code and include `error.code` and `error.message`. `inspect` returns the upstream action tree flattened in depth-first order; each `parent` is the zero-based action array index or `-1` for a root. Each action's `api_events` preserves upstream order and includes its own event as well as preceding API calls. Each entry has an `event_id`, nullable `chunk_index` (null denotes upstream `NoChunk`), structured chunk `name` (empty when unavailable), and decimal-string `file_offset`, a relative stream offset rather than an on-disk file position. It also includes texture metadata; `bytes` is a decimal string to preserve the complete 64-bit value in JavaScript. The array ordering is scoped to this replay session and is not a persistent resource identifier. One-shot `select` opens its own replay session, sets an action or listed API event and returns its common pipeline state.

`filter_events` queries the open snapshot using the same expression subset as the event browser: `{"command":"filter_events","expression":"+$childOf(Main) +$action()","show_api":true,"offset":"0","limit":128}`. The optional `show_api` defaults to false; the offset is a decimal string and limit is 1–128. Rows contain snapshot-scoped `action_index`, nullable `api_index` and `parent_action_index`, event ID, name and `direct_match`. A group row also reports nullable `group_range` with first/last event and action IDs. Ancestors are included for context with `direct_match: false`; all rows are expanded. Invalid or unsupported expressions return `invalid_filter`. The available subset and regex suffix behavior are described in the project README.

`$annot(key)` and conditions such as `$annot(renderdocx.count >= 42)` or `$annot(renderdocx.pass contains shadow)` query the captured API-event annotations. These are distinct from bookmarks and notes. The filter also supports exact string equality and `=~ /regex/`, and works with `find_event`, `step_action`, and `export_events`. Annotation queries require a bridge with `annotation_find`; older bridges return an error rather than silently treating annotations as absent. Quoted keys and Unicode case folding have not been exhaustively compared with upstream.

Agents can inspect specific event annotation values with `{"command":"event_annotation_find","event_id":42,"keys":["renderdocx.pass","renderdocx.count"]}`. The response returns `keys` and matching `values` in the same order; missing keys are `null`. Values are structured nodes, and each request accepts 1–128 keys.

`filter_events` accepts an optional string `annotation_key` and returns its formatted value as each row's `annotation`, or `null` if absent. An empty key hides values. The column is evaluated for the capture before pagination and may take time; unsupported value formats return `replay_event_annotation_failed` rather than partial results.

`filter_events` also accepts `show_empty_regions` (default `true`) and `collapsed_events` (an array of event IDs). Each requested group and its filtered descendants are collapsed before pagination; unknown IDs return `invalid_arguments`, while non-group or currently filtered-out IDs have no effect. Rows expose `has_children` and `collapsed`. `find_event`, `step_action`, and `export_events` accept the same `show_empty_regions` option; export is independent of interactive collapse state.

`export_texture` accepts an optional `display_range` array `[black, white]`, for example `{"command":"export_texture","index":0,"path":"mapped.png","display_range":[0.25,0.75]}`. Values must be finite with black below white. The matching bridge passes them to RenderDoc `TextureSave`; RenderDoc can bypass conversion for already compatible formats, in which case the mapping has no effect. Pixel analysis and raw exports are unaffected. A bridge without the range command returns an error.

A capture snapshot can include `local_renderer`, the numeric RenderDoc `GraphicsAPI` used for rendering, which may differ from the capture `api` during remote replay. Older bridges omit this field.

`export_texture` accepts an optional `export` object: `all_mips` (boolean), `slices` (`selected`, `all`, `grid`, or `cubemap`), `grid_width` (positive integer), `samples_as_array` (boolean), `alpha` (`preserve`, `discard`, `blend_to_color`, or `blend_to_checkerboard`), `alpha_color` (four finite components from 0 to 1), and `jpeg_quality` (1–100). For example, `"export":{"slices":"grid","grid_width":2}` lays out array slices in two columns. Values are passed to the matching RenderDoc `TextureSave`; RenderDoc may adapt them to the resource or output format, including falling back to a single mip or slice. Cubemap cross requires a six-face non-multisampled cubemap. Non-default options require an updated bridge. D3D11 fixtures verify array grids, DDS mip count, BMP alpha blending and JPEG encoding quality; cubemap, multisample mapping and other APIs still need real-capture validation.

`render_texture` renders the native RenderDoc texture display to a new RGB PNG, for example `{"command":"render_texture","index":0,"width":512,"height":360,"path":"preview.png","display_range":[0.25,0.75]}`. The event must be selected first. The width and height are explicit output dimensions; the texture is fitted inside them. It uses the same mip, slice, sample, channel and preview type-cast fields as `export_texture`. It requires a bridge with headless rendering support and never overwrites an existing file. Driver/API behavior beyond the tested D3D11 path remains unverified.

Optional preview-only fields are `preview_channels` (four booleans in RGBA order), `preview_flip_y` (boolean), and `preview_linear_as_gamma` (boolean, default `true`). When `preview_channels` is supplied it overrides the single `channel` for rendering; `channel` still controls single-channel texture export. The new options require an updated bridge; default rendering remains compatible with bridges that implement the original render command.

For `render_texture`, `preview_scale` is a positive finite scale (1.0 is 100%), and `preview_offset` is a two-element array of finite output-pixel offsets, for example `"preview_scale":2.0,"preview_offset":[4.0,0.0]`. Omit the scale and offset to fit the texture; nonzero offsets require an explicit scale. These fields affect preview only and require an updated bridge. The D3D11 fixture exercises this path.

Preview mode can be set with `preview_hdr_multiplier` (finite, non-negative RGBM multiplier) or `preview_decode_yuv: true` (YUVA decode). They are mutually exclusive; omit both for RGBA. RGBM disables the alpha display channel, as in RenderDoc; a zero multiplier does not enable RGBM conversion on the D3D11 backend. These options affect preview only and require an updated bridge. RGBM has targeted D3D11 fixture coverage; real YUV textures remain unverified.

`preview_background` supplies a four-element sRGB RGBA array with finite components from 0 through 1 to `render_texture`, for example `[1,0,0,1]` for red. Omit it or pass `[0,0,0,0]` for RenderDoc's checkerboard. When the alpha channel is displayed with RGB, RenderDoc blends the texture against the background. Background changes require an updated bridge and affect preview only. A D3D11 fixture checks the solid background; transparent texture blending and other APIs remain unverified.

Set `preview_custom_shader: true` on `texture_statistics` or `export_texture` to operate on the active custom shader output. Statistics report `custom_shader: true` and use the generated texture's slice and sample zero; exports follow RenderDoc's mapping behavior for that generated texture. If the custom shader or output is unavailable the request fails explicitly. An updated bridge is required. D3D11 HLSL tests cover min/max, histogram, PNG export and a custom output channel on a single-channel input; other formats, mips, slices and APIs remain unverified.

`pick_custom_pixel` accepts the same coordinates and selection as `pick_pixel` with `preview_custom_shader: true`. Its `pixel` contains the original texture value in the usual fields and the shader result in `pixel.custom`; when a supported debug overlay is selected, the usual fields instead use the overlay value when available and `pixel.overlay` identifies the source. It requires an active custom shader and an updated bridge. Overlay replay invalidates dependent caches and restores the selected event. D3D11 HLSL and its combination with Quad Overdraw Draw have real-capture coverage; other APIs and shader formats remain unverified.

`pick_overlay_pixel` accepts the same coordinates and selection fields as `pick_pixel`, with `preview_overlay` set to `quad_overdraw_pass`, `quad_overdraw_draw`, `triangle_size_pass`, or `triangle_size_draw`. The returned `pixel.overlay` is `true` if the overlay texture was available; otherwise RenderDocX follows the upstream fallback to the original texture and returns `false`. This command can replay the event, restores the selected event and invalidates replay-derived caches. Ordinary `pick_pixel` reads the original texture. A D3D11 quad-overdraw draw and fallback are tested; the remaining modes and APIs require real-capture validation.

`custom_shader_info` lists the replay device's supported numeric `ShaderEncoding` values and source prefixes. `custom_shader_build` accepts `encoding`, `entry`, exactly one of UTF-8 `source` or binary `source_hex`, optional `flags` (`[{"name":"...","value":"..."}]`) and optional `apply_prefix`. The prefix defaults to enabled for GLSL, HLSL and Slang, and disabled for binary encodings. It returns `compiled`, `active` and compiler `diagnostics`; a failed compilation preserves the previous shader. Set `preview_custom_shader: true` on `render_texture` to use the active shader; it is mutually exclusive with RGBM and YUVA decode. `custom_shader_clear` releases it, and closing the session also frees it. The active shader is session-scoped. D3D11 HLSL has real-capture coverage; other encodings and backends require validation.


The desktop and Agent share a local custom shader library. `custom_shader_library_save` accepts `shader` with `name`, numeric `encoding`, `entry`, hexadecimal `source_hex`, optional `flags`, and boolean `apply_prefix`. It refuses to replace an existing name unless `replace: true` is explicitly supplied. `custom_shader_library_list`, `custom_shader_library_get`, and `custom_shader_library_delete` manage records without an open capture; `custom_shader_library_build` loads and compiles a named record against the open capture. `RENDERDOCX_CONFIG_DIR` isolates this library. Binary encodings use hexadecimal input in the desktop editor. Imported flags and prefix settings are retained, but are not yet editable in the desktop. Use `custom_shader_library_import_directory` with `path` to import snapshots of supported upstream `.hlsl`, `.glsl`, `.frag`, `.spvasm` and `.slang` files. The per-file results report successes and failures; existing library names are never overwritten, and the original files are not changed. Like the upstream extension map, `.spvasm` maps to OpenGL SPIR-V assembly. Imports do not watch files or synchronize later changes, and changes require a fresh import.


`custom_shader_build` and `custom_shader_library_build` accept an optional `processor` object in the same format as `shader_apply`. Its input encoding must match the source and its output must be supported by the replay device. The source prefix is applied before processing; the processor receives the pixel stage and the output is compiled without a second prefix. Processor diagnostics are returned as `processor_diagnostics`; processor failure leaves the active shader intact. The desktop automatically uses the first matching configured processor only when the source encoding is not directly supported. D3D11 tests cover a local pass-through processor; other processors and graphics APIs require verification.

`preview_overlay` selects a RenderDoc debug overlay for `render_texture` only. Its default is `none`; `capabilities.texture_overlays` lists the supported values. For example, add `"preview_overlay":"drawcall"` to highlight the selected draw or `"preview_overlay":"clear_before_draw"` to view it after a clear. Overlay availability depends on the selected event, texture and backend. Non-default overlays can replay the event, so the helper restores the selected event and invalidates dependent caches after rendering. An unavailable overlay is reported as an error when detected. These options require an updated bridge. Draw highlighting and clear-before-draw restoration have been exercised with a D3D11 capture; other modes and APIs need further validation.

`$param(Topology: value)` also searches structured API parameters by case-sensitive name and case-insensitive value substring. The same filter works with `find_event`, `step_action`, and `export_events`; resolving it can be slow on large captures. A matching current bridge batches parameter-name searches for each event; older bridges fall back to paged traversal. Resource values use capture names and saved overrides; older bridges lacking resource identity and replacement state cannot evaluate those values. Floating-point and offset/size values use RenderDoc's default formatting settings; configurable formatting and GPU address values are not yet supported. Numeric rounding and Unicode case folding are not yet verified against upstream in every edge case.

Named expressions are shared with the desktop: `event_filter_save` takes `name` and `expression`; `event_filter_get` and `event_filter_delete` take `name`; `event_filters_list` lists all saved expressions. These commands do not require an open capture. Empty and currently unsupported expressions can be saved, but applying an unsupported expression still returns `invalid_filter`. Names are encoded for storage and do not become filesystem paths. Use `RENDERDOCX_CONFIG_DIR` to select an isolated configuration directory.

`export_events` writes that filtered hierarchy to a new UTF-8 text file: `{"command":"export_events","path":"events.txt","filter":"$action()","show_api":false}`. Filter and show_api are optional; all admitted descendants are exported even if collapsed in a GUI. Existing files are never overwritten. Cached GPU durations are included when available. Fully formatted upstream API-call names are not yet represented.

`step_action` returns the previous or next action on RenderDoc's reconstructed action chain: `{"command":"step_action","direction":"next","event_id":42,"filter":"$action()"}`. The event ID defaults to the currently selected event; filter is optional. The response contains the action's session-scoped index and event ID, or null at a boundary. This command does not replay the action; use `select` to do so. The virtual capture-start row is not yet represented.

`find_event` uses the same navigation as the GUI: `{"command":"find_event","query":"@42","direction":"next","filter":"$action()","show_api":true}`. Optional `current_event` controls where a name search starts; direction is `next` (default) or `previous`. The result is a session-scoped event/action/API identity, or null if no eligible match exists. Use `select` separately to replay it. EID navigation advances to the next eligible EID when the requested row is filtered out.

`{"command":"event_times"}` collects the RenderDoc GPU duration counter for the current capture, computes nested marker totals, and caches results for `filter_events`. Rows then include `duration_seconds` when available; duration filters such as `$action(duration >= 1ms)` and `$dispatch(duration < 100us)` become usable. Collection performs GPU replay, invalidates the previous counter generation and mesh cache, and can be expensive. A missing counter returns `counter_unavailable`; times are cleared on capture changes and shader edits.

Pipeline state includes a nullable `scissors` array with each rectangle's signed coordinates, size, and enabled flag. The arrays use each API's own scissor count, which can differ from the viewport count. D3D11 scissor state has been checked against a captured draw; other APIs still require replay validation.

The nullable `fixed_state` contains the upstream common raster, depth, stencil and color-blend state. Enum fields are numeric values from the matching RenderDoc headers; non-finite bounds or blend factors become null. D3D11 capture checks cover raster values and the presence of depth, stencil and blend data. Other graphics APIs, detailed state combinations and GUI interaction remain unverified.

Shader reports include `constant_block_details`, `sampler_details`, `read_only_details`, and `read_write_details`, including nested reflected type and variable layouts. `default_value` is a decimal string. Binding numbers and spaces are upstream reflection metadata, not necessarily actual dynamic bindings (notably on OpenGL); use descriptor inspection for runtime binding information. This is reflection metadata, not decoded constant values.

`{"command":"shader_constants","stage":"compute","block":0,"element":0}` reads the selected event's constant block through RenderDoc's dynamic descriptor mapping and constant-buffer decoder. `block` is the index in shader reflection; `element` defaults to zero. Values and nested members use the same raw `value_hex` representation as shader debugging; offsets and sizes are decimal strings. An unbound buffer or invalid element returns an error. A D3D11 capture validates a bound compute constant; other APIs, inline data and additional binding forms remain unverified.

`{"command":"shader_bindings","stage":"compute","kind":"read_write","offset":"0","limit":128}` pages the selected stage's runtime descriptor accesses. Kinds are `constants`, `read_only`, `read_write`, and `samplers`; offset defaults to `"0"` and limit defaults to 128. Entries include reflection index, array element, static-unused flag, store location and resolved descriptor or sampler details, including descriptor `format_component_type`. Descriptor buffer offsets include RenderDoc's Vulkan dynamic-offset adjustment. A D3D11 compute capture validates constant and read/write resource bindings; other APIs and descriptor forms remain unverified.

`{"command":"shader_binding_read","stage":"compute","kind":"constants","row":"0","offset":"0","length":64}` reads bytes relative to a runtime buffer binding. The binding range is clipped to the captured resource; a read at its end returns no bytes and a read crossing the end is shortened. `row` and `offset` are decimal strings, and `length` is at most 65,536 bytes. D3D11 capture coverage checks a constant buffer and a boundary-crossing read.

Pipeline `color_attachments`, `depth_attachment`, and `depth_resolve_attachment` expose resource and view references, format, texture type, mip/slice range, minimum LOD clamp, and swizzle from RenderDoc descriptors. Existing `outputs` remains available. Non-finite LOD clamps are null. D3D11 color and unbound depth were checked with a capture; bound depth, resolves and other APIs remain unverified.

`export_texture` accepts `preview_type_cast`, a numeric RenderDoc `CompType` (0 through 9, default 0), passed to `TextureSave.typeCast` for PNG export. Pixel picking, statistics and history accept the separate `analysis_type_cast` field with the same range and default. Neither field applies a descriptor swizzle. A D3D11 capture exercises these operations with a type cast; additional formats, results and APIs require further validation.

`serve` keeps replay and target sessions open and accepts one JSON object per stdin line. It handles requests sequentially and emits exactly one JSON response per line on stdout, using `schema: "renderdocx.agent.v1"`, echoing the optional `id`, and returning either `data` or `error.code`/`error.message`. Commands include `capabilities`, `open`, `snapshot`, `select`, `pipeline`, `shader`, `debug_vertex`, `debug_pixel`, `debug_compute`, `debug_next`, `debug_stop`, `vertex_input`, `mesh`, `mesh_read`, `structure`, `read_buffer`, `resource_usage`, `pick_pixel`, `pixel_history`, `texture_statistics`, `export_texture`, `close`, the target commands below, and `quit`.

The capture `resources` array is ordered by RenderDoc's session resource list. Each entry includes its name, numeric upstream `ResourceType`, autogenerated-name flag, initialization chunk indices and `parents`/`derived` references into the same array. A null relationship means the referenced resource is absent from this list. These indices are session-scoped, not persistent resource identifiers; chunk indices refer to the structured capture, not event IDs. Older bridges may omit this array.

The snapshot also contains `frame_info` (64-bit sizes, relative file offset and UTC capture timestamp as decimal strings), `frame_statistics` and `debug_messages`. Statistics contain RenderDoc's recorded per-category data; when `recorded` is false, the other statistic fields are unavailable. Messages contain upstream numeric category, severity, source, message ID, event ID and full text. The initial snapshot contains opening-time messages; `debug_messages` polls the replay driver and appends later messages to the session's snapshot. Older bridges may omit these fields.

`{"command":"annotation_read","name":"notes"}` or `name: "bookmarks"` reads the corresponding RenderDoc version-one JSON section and returns both its parsed `document` and the original `section` token. To save, send `{"command":"annotation_write","section":<original section>,"document":<updated object>}`. Preserve keys you do not edit: notes use `comments`, and bookmarks use `Bookmarks` entries containing `eventId` and `text`. The helper checks the original bytes and section version before writing; the Rust session also checks file size and timestamps and invalidates its structured-data worker. These metadata checks and the section comparison are not a cryptographic or atomic lock against concurrent writers. Saving modifies the capture file; use a copy when needed. Unsupported versions and invalid JSON are rejected. GUI comments require an explicit save and unsaved drafts prevent switching captures through the application's controls. The GUI also blocks ordinary window-close requests while a comment draft is unsaved or a replay, resource or export operation is in progress. Forced process termination and broader interoperability remain outside this protection.

`{"command":"resource_rename","index":0,"name":"New name"}` saves a resource name in RenderDoc's version-one `ResourceRenames` section; an empty name removes the override. The index addresses the current snapshot only, while its `rename_key` is the stable RenderDoc `ResourceId::<decimal>` key used in the capture. `annotation_read` also accepts `renames`, whose `CustomResourceNames` object preserves other resource names and unrelated fields. The Resources list and filter, resource relationships, texture and buffer views, shader list, descriptor stores and pipeline summary show overrides when resource indices are available. Other views do not yet consistently use them. Texture resource indices may be null or absent when using an older bridge. Saving has the same concurrent-writer limitations as other annotation writes.

`{"command":"debug_messages","offset":"0","limit":128}` drains newly queued RenderDoc messages, appends them in arrival order, and returns a page of the accumulated messages with decimal-string `offset` and `total` and the number newly `added`. Offsets are scoped to the current open capture and remain stable until cleared. `{"command":"clear_debug_messages"}` clears the accumulated list; it does not discard messages still queued by the replay driver, which will be included by the next poll. The GUI polls while a capture is open and supports text, severity, source, category and message-type filtering. Messages can be generated by replay and device operations, so an empty poll does not establish that validation is enabled or that the capture is error-free.

The snapshot's `counters` array lists the GPU counters exposed by the active replay device, including the upstream ID, name, description, category, UUID words, result type, byte width and unit. Request a measurement with `{"command":"counter_fetch","counters":[1,2]}` using IDs actually present in that array. Measurement replays GPU work, can take time, invalidates cached mesh and pixel-history data, and restores the selected event afterwards. Its response contains decimal-string `generation` and `total`. Read pages with `{"command":"counter_page","generation":"1","offset":"0","limit":128}`; a later fetch invalidates earlier generations, which are scoped to the current replay session. Each result contains an event ID, counter ID, and unsigned decimal-string `bits`: interpret 32 or 64 bits using the counter's `result_type` and `result_byte_width`, preserving exact integers and non-finite floating-point values. Available counters and result coverage depend on the replay driver and hardware. This is an initial implementation, not a guarantee of all vendor counter workflows.

The snapshot's `descriptor_stores` list exposes each RenderDoc descriptor store's session-scoped resource index, descriptor size, first offset and count. After selecting an event, `{"command":"descriptors","offset":"0","limit":128}` pages descriptor accesses returned by `GetDescriptorAccess`; an optional `store_index` instead pages a fixed-size descriptor store. This distinction matters on fixed-binding APIs such as D3D11, which can report accesses without exposing stores in the global list. Entries include available descriptor, logical location and sampler data; resource references are nullable indices into the snapshot resource list, while 64-bit buffer ranges are decimal strings. Float fields that may be non-finite are represented by their 32-bit patterns. Null data means the replay driver did not return it. Results describe the selected event and must be reread after event changes. Variable-sized stores cannot yet be enumerated using the store mode; dynamic descriptor access, indexing semantics and data availability remain driver-dependent.

`resource_usage` reads RenderDoc's static usage for one resource without changing the selected replay event: `{"command":"resource_usage","index":0,"offset":"0","limit":128}`. The index refers to the capture `resources` array; offset is an unsigned decimal string, and limit defaults to 128 and must be 1–128. `total` and `offset` are decimal strings. Entries preserve upstream order and report `event_id`, numeric `ResourceUsage` and a convenience `usage_name`. `tracked: false` preserves RenderDoc's single event-0 `Unused` sentinel for resource types whose usage is not tracked; an empty tracked list instead means no static usage was observed. An event need not have a navigable action in the capture. Paging limits the IPC response; RenderDoc's underlying API returns the entire usage list for each request. Real D3D11 and OpenGL coverage includes vertex-buffer draws; D3D11 also covers an untracked shader. Other resource types and APIs need additional validation.

`structure` reads a page of direct structured-data children for any event with an available chunk, independently of the selected replay event. Use `{"command":"structure","event_id":42,"path":["0"],"offset":"0","limit":128}`. `path` is a sequence of decimal-string child indices from the chunk; it and `offset` default to the root and zero. `limit` defaults to 128 and must be 1–128. The reply contains the requested `node`, its `children`, `event_id`, `path`, and `offset`. `child_count` and `byte_size` are decimal strings, as are numeric scalar `value`s; boolean values are strings `true` or `false`, and character values are unsigned byte strings. Strings retain their UTF-8 content. `basic_type` and `flags` are upstream `SDBasic` and `SDTypeFlags` values; `custom_string` preserves upstream display metadata. Resource objects report `resource_non_null` and a session-scoped `resource_index` when available, rather than exposing the opaque `ResourceId`. Missing chunks and invalid paths return errors. This exposes structured data rather than reproducing every RenderDoc formatting rule.

`decode_buffer` interprets a bounded page as one scalar type, for example `{"command":"decode_buffer","index":0,"offset":"0","length":64,"format":"float"}`. Supported formats are `bool`, `ubyte`, `byte`, `ushort`, `short`, `uint`, `int`, `ulong`, `long`, `half`, `float`, `double`, `unormb`, `snormb`, `unormh`, and `snormh`. Values and absolute byte offsets are strings, preserving 64-bit integers and non-finite floats; `trailing_hex` preserves an incomplete final element. Decoding begins at the requested byte offset in little-endian order. This is a scalar subset, not RenderDoc's full custom buffer format language.

Saved buffer formats are shared with the desktop buffer viewer and do not require an open capture. `buffer_formats_list` returns `{formats:[{name,layout}]}`; `buffer_format_get` accepts `name`; `buffer_format_save` accepts `name` and `layout` and replaces an existing name; `buffer_format_delete` accepts `name`. Names must be nonempty, trimmed, and free of control characters. Each definition is saved independently using an encoded filename and an atomic replacement. `RENDERDOCX_CONFIG_DIR` overrides the root for this format store (useful for isolation); otherwise it uses the RenderDocX configuration directory. Saved text may include syntax not yet implemented; applying it still performs the current parser and capture API checks.

`export_buffer_csv` streams a decoded layout to a new local file: `{"command":"export_buffer_csv","index":0,"offset":"0","length":"64","layout":"float3 position; uint id;","scope":"repeating","path":"buffer.csv"}`. `scope` is `repeating` (default) or `fixed`; fixed scope exports a single fixed layout or the fixed prefix of a repeating layout. CSV columns are `Byte Offset` followed by flattened field names; vector and array values are quoted as needed. The response reports decimal-string `rows` and `trailing_bytes`. An incomplete final repeating row is not exported. Selection changes, incomplete reads, invalid layouts and existing destinations fail without publishing a partial file. This schema is RenderDocX's field-oriented CSV and is not identical to all upstream viewer CSV variants.

`decode_buffer_layout` decodes repeated rows using a restricted RenderDoc declaration subset: `{"command":"decode_buffer_layout","index":0,"offset":"0","length":64,"layout":"#pack(scalar) float3 position; uint id;"}`. It supports named scalar and 2–4 component HLSL/GLSL vector and matrix fields, fixed positive arrays, `signed` / `unsigned` qualifiers, the legacy `rgb` qualifier, C-style comments, `#pack(scalar)`, `#pack(structured)`, `#pack(std430)`, `#pack(std140)` and `#pack(cbuffer)`, and the `[[offset(n)]]` / `[[byte_offset(n)]]`, `[[pad]]` / `[[padding]]`, `[[unorm]]`, `[[snorm]]`, `[[row_major]]`, and `[[col_major]]` annotations. Matrix declarations default to column-major storage; `row_major` and `column_major` keywords are also accepted. Matrix values are flattened in logical row-major order and include `matrix_rows`, `matrix_columns`, and `row_major` metadata. Explicit offsets are decimal and cannot overlap preceding data. It applies the selected mode to field alignment, arrays, matrices and nested structures; the response reports the selected `packing`. Rows expose field offsets and array/component values as strings, and `trailing_hex` contains incomplete final-row bytes. `[[rgb]]` marks a field for color display; `rgb_srgb8` contains an RGB byte triple per array element when its type is supported. Floating-point, normalized, and normalized packed values are clamped as linear RGB then converted to sRGB; integer values are clamped directly to 0–255. NaN and types without a color interpretation produce null. `[[hex]]` / `[[hexadecimal]]`, `[[bin]]` / `[[binary]]`, and the integer aliases `xbyte`, `xshort`, `xint`, `xlong` supply a `display` mode and width-padded `display_values`; numeric `values` remain machine-readable, with signed integers interpreted as unsigned bit patterns as in RenderDoc. Float, packed and enum fields cannot currently use these display annotations. With normalized integers, the normalized numeric value remains the displayed value. Previously declared integer-based enums and `[[flags]]` / `[[mask]]` enums are supported, with decimal or hexadecimal constants and fixed arrays; leading-zero integer literals follow the upstream base-detection behavior. The response retains numeric strings and includes `enum_type`, `enum_flags`, and per-element `enum_names`; unknown values have an empty name list. Previously declared named structures and fixed structure arrays are supported; struct definitions accept `[[size(n)]]` / `[[byte_size(n)]]` and `[[align(n)]]` / `[[alignment(n)]]` (nonzero alignment must be a power of two), with explicit size no smaller than the derived size; nested leaf names are flattened as `parent.child` or `parent[0].child`, with absolute offsets. Definitions must precede root variables; when no root variable is declared the last defined structure is used. A final unbounded array is supported at the root or down the final chain of nested structure members, optionally after a fixed prefix. Arrays of structures that themselves contain an unbounded array and multiple nested unbounded arrays remain unsupported. For subsequent pages provide the original layout start as the decimal-string `origin`, and use a repeated-element-aligned `offset`. The first page includes `fixed`; later pages may set `"include_fixed":true` to read and include the fixed prefix from the same replay selection. `repeat_offset` reports the absolute start of repeated elements; the fixed-prefix read is independently limited by the buffer page limit. The selected capture API is checked: Direct3D requires an unbounded array to be the only root variable. `[[single]]` or `[[fixed]]` on a sole root variable, or on the final implicit struct definition, decodes a single fixed layout into `fixed` with no repeated rows. Forward declarations, pointers, inline nested definitions, other packing modes and other annotations are rejected. It also supports `[[packed(r10g10b10a2)]]` with unsigned integer or compatible normalization, explicit `r10g10b10a2_uint`, `r10g10b10a2_unorm`, `r10g10b10a2_snorm`, and `r11g11b10`, plus `uintten`, `unormten`, and `floateleven` aliases. Packed fields consume four bytes per element and include a `packed` identifier in the response. Other packed formats are rejected. Constant-buffer arrays and matrices whose vector size exceeds 16 bytes are currently rejected. Named integer and enum bitfields, including anonymous padding fields, use the upstream non-tight rollover rules. Bitfield responses include `bit_offset` and `bit_size`; signed values are sign-extended. Bitfields on bool, floating, vector, array or packed fields and tight bitfield packing are not supported. The default is scalar packing, including for constant buffers whose upstream default may differ; specify a supported packing explicitly when needed. GUI layout rows are paged at whole-row boundaries, with a row limited by the replay page size.

`find_buffer` searches a selected event's raw bytes within a range, for example `{"command":"find_buffer","index":0,"offset":"0","length":"65536","hex":"00 01 ff"}`. Offset and length are decimal strings; the nonempty hex pattern may contain ASCII whitespace. The response offset is a decimal string or null when no match exists. Search streams bounded pages and finds patterns crossing page boundaries. Large ranges can take time and hold the replay session until the search finishes. GPUI searches the current buffer or binding range from the displayed offset; repeat **Find next** to continue after the previous match.

`export_buffer` streams the selected event's raw buffer range to a new file: `{"command":"export_buffer","index":0,"offset":"0","length":"65536","path":"C:/captures/buffer.bin"}`. Offsets and lengths are decimal strings; the range must fit the captured buffer. Data is read in bounded pages into a temporary file and published only on success; existing destinations are not overwritten. A short read or a replay selection change detected before publication aborts the export. GPUI exports the currently viewed binding range, or the full buffer when no binding range is active.

`structure_buffer` reads raw bytes for an upstream `SDBasic::Buffer` node, for example `{"command":"structure_buffer","event_id":42,"path":["3"],"offset":"0","length":256}`. The response includes lowercase `hex`; offsets are decimal strings and each request is limited to 65,536 bytes. The first read opens an isolated structured-data worker and asks RenderDoc for the complete structured capture export, which can require substantial extra memory and time; the worker is reused for subsequent pages and closed with the session. The helper checks matching event and chunk metadata and refuses reads if file size or timestamps changed since opening. These metadata checks are not a cryptographic content-integrity guarantee. Reading structured bytes does not change the primary replay selection.

`pick_pixel` uses RenderDoc's `PickPixel` at the selected replay event, for example `{"command":"pick_pixel","index":0,"mip":1,"slice":0,"sample":0,"x":3,"y":2}`. Coordinates are in the selected mip and have a top-left origin on every API. Mip and slice default to zero; a null or omitted sample requests upstream resolve for multisampled textures and sample 0 for single-sample textures. `pixel.sample` is the actual upstream sample argument, with 4294967295 denoting resolve. The request validates coordinates and subresources. `channel`, when supplied, is validated but does not filter this RGBA result. `bits` contains the four 32-bit component patterns returned by RenderDoc; `float_values`, `uint_values` and `int_values` are alternative interpretations of those same bits, with floats encoded as strings to preserve non-finite values. They are not raw texture storage bytes. RenderDoc's API does not return an individual success status for every pixel read; supported formats and drivers determine the result. Real D3D11 tests cover mip/slice, one 3D slice, unsigned integer textures and, when supported, a uniform multisampled texture; an OpenGL test checks top-left orientation. Varying multisample values, other 3D cases, other APIs and formats still require real-capture validation.

`pixel_history` calls RenderDoc's `PixelHistory` for the selected event, for example `{"command":"pixel_history","index":0,"x":8,"y":8,"offset":"0","limit":128}`. It returns modifications up to and including the selected event, preserving fragment and primitive indices, test-failure flags, direct-write and unbound-shader flags, and before, shader-output and after values. RenderDoc filters out CPU writes, resource discards and read-only usages. Null values are upstream invalid-value sentinels; color and depth bit patterns are retained and accompanied by interpretations, while stencil values preserve upstream negative sentinels. Coordinates use the selected mip and a top-left origin. `channel` is validated but does not filter history. For multisampling an omitted sample passes the upstream default sentinel; backend behavior differs, so specify a sample for an unambiguous request. In particular, the current D3D11 backend maps that default to sample 0. `offset` and `total` are decimal strings and limit defaults to 128 with a maximum of 128. The helper caches the complete upstream result for subsequent pages and frees it on event change or a new query; computing it can involve substantial replay work and memory. Calling history invalidates the current agent mesh selection, and the selected replay event is restored by RenderDoc. An empty list can mean no relevant writes or that the upstream backend could not inspect the pixel; the API does not provide a separate success status. Real D3D11 coverage includes a clear, successful fragment and scissor-rejected fragment; OpenGL coverage includes a clear and successful draw. In one OpenGL fixture, an FBO bound before capture without an in-capture rebind produced no target usage or history despite a visible draw; rebinding it during capture recorded the history. Other APIs, multisample histories and formats need additional validation.

`texture_statistics` calls RenderDoc's `GetMinMax` and `GetHistogram` for a selected event and subresource, for example `{"command":"texture_statistics","index":0,"mip":0,"slice":0,"min":0,"max":1,"channels":[true,false,false,false]}`. The range defaults to 0–1 and must remain finite, ordered and representable in float32, including its span and RenderDoc's upper-bound adjustment. `channels` is an optional four-boolean RGBA mask; when omitted it follows the selected `channel`, or all available components if no channel is selected. Minimum and maximum always cover RGBA independently of this histogram mask. The response preserves each extreme's returned 32-bit component patterns with float, unsigned and signed interpretations, plus the upstream unnormalized histogram array; an empty array means no histogram was returned. RenderDoc's public `GetMinMax` does not expose the underlying success flag and may return default values on failure, so these extrema alone do not establish success. D3D11 tests cover an array mip, one 3D slice and an unsigned integer texture; when supported, the fixture also checks a uniform multisampled texture and its resolve. OpenGL tests check histogram counts. Varying multisample values, other 3D cases and other graphics APIs still need real-capture validation.

Live control uses the matching `renderdocx-target` helper next to the configured replay bridge. `target_list` enumerates RenderDoc target identifiers; `target_connect` takes a nonzero `ident`. Both accept an optional nonempty RenderDoc `url`; omitting it targets the local machine. `target_connect_pid` takes a nonzero `pid` and searches available local targets by process ID. Neither force-disconnects a busy client; PID lookup briefly probes other available local targets while searching. `target_launch` takes an executable `path`, an existing absolute `capture_directory`, and optional platform-specific raw `arguments`; each launch creates a fresh session subdirectory to avoid overwriting captures from earlier runs, and returns its `capture_template`. `target_trigger` takes nonzero `frames`; `target_queue` additionally takes the target `frame`; `target_cycle` changes the active window. These return `submitted` when the request is written to the helper, not when the target has captured a frame. Poll `target_events` to receive API registration, command-sent, capture, progress, child, window and disconnect notifications. A capture event's `path` is usable locally only when `local` is true. `target_close` disconnects without terminating the target; `quit` also closes the connection. Only one target session is held at a time. Remote discovery and non-forced connection have been tested via loopback. Remote capture copying over a loopback target has been tested with byte-for-byte comparison. Cross-machine connectivity and copying, injection into an already-running process, and remote replay remain unverified or unimplemented.

`{"command":"target_copy","capture_id":0}` requests a target capture copy into a fresh application-owned directory; an optional `capture_directory` selects an existing absolute parent directory. `submitted` means the request was sent, not that the file is ready. Poll `target_events` for a matching `copied` event and its local path. A duplicate request for the same capture is rejected until completion is consumed. Interrupted or failed transfers can leave incomplete files; completion checks a nonempty file but does not validate its capture contents.

For `target_launch`, optional `configuration` accepts `arguments`, an absolute existing `working_directory` (null uses the executable directory), `options`, and `environment`. For example:

```json
{"command":"target_launch","path":"C:/game/Player.exe","capture_directory":"C:/captures","configuration":{"arguments":"-screen-width 1280","working_directory":"C:/game","options":{"api_validation":true,"capture_callstacks":true},"environment":[{"name":"EXAMPLE_PATH","value":"C:/example","operation":"prepend","separator":"platform"}]}}
```

`capabilities.capture_options_default` exposes all 12 upstream options and defaults. `delay_for_debugger` is in seconds and `soft_memory_limit` in MB; the latter is an upstream soft target, not a hard limit. Each environment entry requires `name`, `value`, `operation` (`set`, `append`, `prepend`) and `separator` (`platform`, `semi_colon`, `colon`, `no_sep`). Entries are applied in order by RenderDoc. Unknown configuration fields are rejected. The older top-level `arguments` remains accepted when `configuration` is omitted. Environment values are sent to the RenderDocX helper through stdin and are not saved in RenderDocX settings or echoed in responses; the launched target necessarily receives them in its environment. On Windows, upstream's cross-bitness injection path may pass environment values through an additional helper's command line. Application arguments remain visible to the operating system as part of the target command line. The GUI also supports ordered environment modifications and masks the value input.

An unsuccessful `open` leaves the previous session intact. `pipeline` requires a selected event and returns RenderDoc's common topology enum, shader stages, output bindings, index and vertex buffers, vertex input metadata, and viewports. `resource_index` is the index in the upstream resource list for this session only, or null when the resource is absent from that list; it is not the texture index or a persistent identifier. Buffer `byte_offset` and `byte_size` are decimal strings preserving upstream 64-bit values, including sentinel sizes that do not represent the actual buffer length. Non-finite viewport coordinates are represented as null. `available: false` means RenderDoc did not provide a pipeline state. OpenGL vertex inputs are built from the pipeline state and shader reflection to avoid uninitialized trailing entries in the upstream common implementation; `vertex_inputs` is null when reflection is unavailable. Generic component bit patterns are exposed as `generic_bits`. New pipeline fields are null when an older bridge does not provide them. This is a subset: API-specific pipeline details, source editing, other shader debug stages, texture raw pixels and remote capture are not yet exposed. `export_texture` requires a selected event and writes PNG by default using RenderDoc's mapping; it never replaces an existing destination. The optional `format` selects `png`, `dds`, `jpg`, `bmp`, `tga`, `hdr`, or `exr`; non-PNG formats require an updated version-matched replay bridge. Raw subresource export uses the separate `export_texture_raw` command. `close` and `quit` wait for the replay helper to shut down, releasing its capture file before acknowledging. The server opens no network listener and performs no authentication; only processes with access to its stdin can send commands.

`shader` inspects the shader bound at the selected event. `stage` is one of the names in `capabilities.shader_stages`; `target_index` is optional and indexes the `targets` array returned for that stage and event. Omitting it or using null asks RenderDoc for its default. The result includes entry point, encoding, signature metadata, resource counts, supported targets, disassembly text, debug availability/status and embedded source files when supplied by RenderDoc. `debuggable`, `source_debug_info` and `debug_status` are null with older bridges; missing source files produce an empty array. RenderDoc may return an error message as the disassembly text; a successful request does not establish that disassembly or decompilation succeeded. Unbound stages and missing reflection return errors.

`shader_export` writes the complete UTF-8 text to a new file: `{"command":"shader_export","stage":"vertex","kind":"disassembly","path":"output.txt"}`. Use `kind: "source"` and `source_index` for an embedded source file; `target_index` is optional and has the same meaning as in `shader`. Existing paths are never replaced. An I/O error after creation may leave a partial file. The GPUI inspector exports the complete selected source file or disassembly, not just its visible page.

`shader_apply` compiles and replaces the shader currently bound at a selected event for the lifetime of the replay session: `{"command":"shader_apply","stage":"fragment","encoding":5,"entry":"main","source":"float4 main() : SV_Target { return 1; }"}`. `encoding` is a RenderDoc `ShaderEncoding` number reported in the shader's `target_encodings`; provide exactly one of UTF-8 `source`, binary `source_hex`, or a `files` array of `{name,contents}` for GLSL, HLSL or Slang. The first file is the entry source and captured files are used to expand includes following the upstream editor's matching and recursion rules. An optional `flags` array of `{name,value}` passes compile flags to RenderDoc; when omitted, the current reflection's flags are used. The response contains `edit.applied`, compiler `diagnostics`, and the refreshed pipeline. A compilation failure removes an earlier replacement for that shader, matching the upstream editing path. `{"command":"shader_revert","stage":"fragment"}` removes the replacement. Applying or reverting replays the event and invalidates mesh, pixel-history and counter results. Replacements are not saved in the capture and are released on session close. External compilers are not handled automatically. Real D3D11 HLSL replacement, include expansion and revert have been checked by pixel comparison; other APIs and encodings remain unverified.

`annotation_read` also accepts `name: "edits"` for RenderDoc's version-one `EditedShaders` editor-draft section; update it with `annotation_write` and the original section token. The GPUI editor can save a draft to this section and reopen a matching shader/stage draft. Saving a draft does not apply a replacement. Other editors and unknown fields are preserved, and ambiguous duplicate matches are rejected. The GUI switches between files while retaining edits and applies stored compile flags. External RenderDoc interoperability and real GUI round-trip validation are still pending.

Agent callers can explicitly supply an external `processor` object to `shader_apply`, for example `{"executable":"glslangValidator","input_encoding":2,"output_encoding":3,"arguments":["-V","-S","{glsl_stage4}","-o","{output_file}","{input_file}"]}`. Arguments are a JSON string array and are passed directly to the executable, without a shell. Supported placeholders are `{input_file}`, `{output_file}`, `{stdin}`, `{entry_point}`, `{glsl_stage4}`, `{hlsl_stage2}`, `{full_stage}`, `{spirv_ver}` and `{vulkan_ver}`. The process runs in a temporary directory containing its input and output files. If `{output_file}` is absent, stdout is the processor output; stderr is returned as `processor_diagnostics`. The requested output encoding must be supported by the replay device. In GPUI, import a JSON object with the same fields plus `name`, then explicitly select the processor and apply the draft. Processor arguments come from the imported configuration; the editor's command-line field is passed to RenderDoc as a compile flag. A saved tool name alone does not execute a program. The CLI passes a headless type check; a subprocess fixture covers stdin, stdout, files, failure and timeout. Real compiler and GUI execution paths have not yet been exercised.

An editable import example is available at `docs/examples/shader-processor-glslang.json`; the executable must be installed and discoverable on `PATH`, or the file must be edited to use its path. This example has not been validated against a real compiler.

An optional positive `timeout_ms` can be included in either CLI or imported GUI processor configuration. On expiry RenderDocX stops the directly launched process and reports an error before applying a replacement. Omitting it leaves execution without a timeout. Child processes started by the processor are not stopped automatically.

`debug_vertex` starts a RenderDoc vertex shader trace for a selected draw: `{"command":"debug_vertex","vertex":0,"instance":0,"index":0}`. `vertex` and `instance` are zero-based positions in the draw, whereas `index` must be the actual vertex input index with all draw offsets applied; use `vertex_input` to inspect the resolved index. `view` defaults to zero and must be smaller than `pipeline.multiview_count`, derived from RenderDoc's `PipeState::MultiviewBroadcastCount()`. Older bridges may omit this count. Nonzero views still need real Vulkan validation. The trace includes inputs, constant blocks, resources and samplers. Each variable contains upstream type, flags, dimensions, recursive members and `value_hex`, the full 128-byte native-endian `ShaderValue` union. The numeric types and flags are RenderDoc enums, and the bytes are not a platform-independent serialized numeric representation.

`debug_pixel` starts a pixel shader trace at the selected draw, for example `{"command":"debug_pixel","x":8,"y":8,"sample":0,"primitive":0}`. Coordinates have a top-left origin on every API. `sample`, `primitive` and `view` may be omitted or null for RenderDoc's `NoPreference`; the numeric sentinel 4294967295 is rejected so it cannot be mistaken for an actual selector. The API debugs the selected draw and does not take a texture identifier or validate coordinates against a particular texture. The backend determines whether a fragment exists and whether a shader can be debugged; failure to create a trace is an error. RenderDoc ignores sample for non-multisampled targets, and some backends can ignore selectors: in the current D3D11 implementation `view` is not used. The helper does not independently verify that an explicit sample, primitive or view was honored. A real D3D11 fixture exercises a passing fragment and its primitive; other graphics APIs, views, multisampling and engines remain unverified.

`debug_compute` starts a compute shader trace for a selected dispatch: `{"command":"debug_compute","group":[1,0,0],"thread":[1,1,0]}`. Both are zero-based three-dimensional indices, with `thread` relative to its workgroup. The helper validates each group component against the action's `dispatch_groups` and each thread component against the action's `dispatch_threads`, falling back to the compute shader reflection's `dispatch_threads` when the action does not specify a thread size, matching RenderDoc's selector. Zero or unavailable dimensions and out-of-range indices fail. The action arrays and shader thread dimensions may be null with older bridges. Trace batches and lifecycle use the same `debug_next` and `debug_stop` contract as vertex debugging. A real D3D11 dispatch verifies nonzero group, local thread and derived dispatch IDs; indirect dispatches, other APIs and engines remain unverified.

`debug_mesh` starts a mesh-shader trace on a selected mesh dispatch with the same `group` and `thread` arrays, range checks, `debug_next`, `debug_collect` and `debug_stop` lifecycle. It calls the upstream `DebugMeshThread` API and rejects a missing mesh shader, missing dimensions, out-of-range coordinates and unavailable debugger. This checkout implements the backend for Vulkan; its D3D11, D3D12 and OpenGL paths do not provide mesh traces. A successful Vulkan mesh trace has not yet been validated.

The returned trace includes `instructions`, a sparse, ordered list of upstream instruction mappings. Each entry contains a 1-based `disassembly_line`, source `file_index`, 1-based source line and column range, and instruction-scoped `source_variables`; a zero line or negative file index indicates missing information, and zero columns indicate a whole-line range. For navigation, lookup follows upstream ShaderViewer: the first entry whose instruction is at least the requested instruction, or the first entry if none exists. The file index refers to the same stage's `shader.source_files`, and disassembly lines refer to its default target, not necessarily an alternate target. `source_variables` at trace level applies throughout the trace; each mapping contains type and dimensions plus its component references to debug variables. Older bridges return empty mapping arrays. These structures can be large, especially when scopes repeat; source files can contain embedded shader source and original file paths.

For stateful navigation, call `{"command":"debug_collect"}` immediately after starting a trace and before any `debug_next`. It reads every remaining upstream batch, frees the backend debugger and retains the complete timeline in the CLI process. `debug_state` returns the current state, source location, position, total and breakpoints. Use `{"command":"debug_breakpoint","breakpoint":{"kind":"source","file_index":0,"line":7},"enabled":true}` or `{"kind":"disassembly","line":14}` to set or remove a breakpoint at an actual mapped location. `{"command":"debug_navigate","direction":"forward","mode":"run"}` runs to a breakpoint, an upstream `DebugBreak` event or a boundary; `direction` can also be `backward`, and `mode` can be `instruction` or `source` for a single instruction or source-location step into. Source stepping falls back to one instruction if the current location has no source mapping. For `run`, optional `event_mask` selects upstream sample/load/gather (1) and NaN/Inf (2) stops; `DebugBreak` (4) is always active. Run moves past the current state, and resuming on a source breakpoint skips consecutive instructions on that line until it is left. Replies identify the stop reason. Event selection, successful capture replacement, `debug_stop` and session closure clear the timeline. If any batch was already read using `debug_next`, collection is rejected to avoid silently dropping earlier states; restart the trace to collect it. The complete timeline and mappings can consume substantial memory. The response includes mutable_variables reconstructed from the recorded changes at the current step; static inputs and resources remain in the trace. Source-level expression evaluation is not yet implemented; step-over and step-out still need real multi-function shader and cross-API validation.

Call `{"command":"debug_next"}` repeatedly: each response contains an upstream batch of states, with step index, next instruction, flags, call stack and reversible before/after variable changes. A batch is not a single step. The first empty batch reports `finished: true`; repeated calls then return an empty finished batch. Each call may take substantial time or memory; no arbitrary step limit is imposed. `debug_stop` frees the trace, as do event selection, opening another capture and closing the session. An invalid start request leaves an existing trace in place; a valid new start replaces it. Starting a debug trace invalidates the selected mesh output. While a trace is active, the primary replay helper rejects unrelated replay operations until it is stopped or an event is selected; debug message polling remains available. Debugging requires support from the upstream backend and shader; failure to create a trace is reported as an error. This is not a full interactive debugger. Real D3D11 vertex, pixel and compute traces are covered, including source mapping for one debug-compiled compute shader; other APIs, shader stages and engine workflows remain unverified.

`debug_navigate` also accepts `mode: "over"` and `mode: "out"` in either direction. These use source locations and the recorded callstack, stopping on breakpoints, stack changes and trace boundaries; when no source location is available, they fall back to one instruction. Missing or incomplete callstacks limit the precision of these operations.

`mesh` queries RenderDoc's generated post-shader output for the currently selected draw or mesh-dispatch action, for example `{"command":"mesh","stage":"vs_out","instance":0,"view":0}`. Stages are `vs_out`, `gs_out`, `task_out`, and `mesh_out`; instance and view default to zero. An unavailable stage may return an unbound resource or an upstream status rather than an error. Task and mesh shader stages are rejected for D3D11 and OpenGL. The view index must be smaller than pipeline.multiview_count, following the upstream viewer. Nonzero views still need real Vulkan replay validation. The result exposes upstream format, topology, strides, index metadata, meshlets and status. Decimal-string offsets and sizes retain upstream sentinel values, which need not equal actual buffer lengths. Non-finite near/far values are null; `dispatch_size` is null when unavailable. Resource IDs are not persistent and are not exposed.

`vertex_input` reads shader input attributes in draw order for a selected draw action: `{"command":"vertex_input","instance":0,"offset":0,"limit":64}`. Instance and row offset default to zero; the limit defaults to 64 and must be 1–64. The reply includes the original and resolved indices, primitive-restart rows, and used attributes. It applies RenderDoc's buffer bindings, draw offsets, base vertex and instance rates. Available values include raw lowercase `hex`; regular float16, float32 and float64, signed and unsigned integers, scaled values, 8- and 16-bit normalized values and selected packed formats also include string `values`. Other formats retain raw bytes and null `values`; supported generic attributes return decoded values without buffer bytes. Out-of-range or unbound inputs are marked unavailable. This command needs a bridge providing draw-offset, format and primitive-restart metadata; it fails when those are absent. D3D11 indexed and OpenGL 3.3 non-indexed vertex input, including a normalized attribute and a generic float attribute, have been verified with actual captures; other APIs and formats require real-capture validation.

After a successful query, `mesh_read` reads its generated vertex or index buffer: `{"command":"mesh_read","kind":"vertex","offset":"0","length":256}`. Offsets are decimal strings relative to the returned buffer offset; length is at most 65,536 bytes, zero returns no bytes, and a short read is reported with its actual length. Changing the selected event, opening or closing a capture, or a failed mesh query invalidates the CLI mesh selection. This is raw buffer order, not reconstructed draw-index order. D3D11 VS output is covered with a real capture; other stages and APIs need real-capture validation.

For aligned 8-, 16-, or 32-bit index reads, `mesh_read` also returns `indices` with decimal-string row, raw index, restart marker, and base-adjusted vertex (null for restart); it is null for other reads or partial indices. As in the upstream buffer viewer, restart is taken from the active indexed draw's pipeline for VS output and is disabled for later stages. This decoding has not yet been validated with captured restart-enabled draws across graphics APIs.

For regular 16-bit and 32-bit floating-point vertex formats, vertex reads also return `positions` with decimal-string row and component values, independent of whether the values are post-projection. Only complete elements in the requested range are returned. Unsupported formats return null; non-finite component values are represented as null by JSON serialization. The raw `hex` remains available.

After `mesh`, `{"command":"mesh_draw","offset":0,"count":64}` returns paged positions in draw-index order for VS/GS/MeshOut. Rows report raw and adjusted indices, restart, and an unavailable reason for unsupported formats or short reads; MeshOut rows also include meshlet and meshlet-local row when available. Non-indexed output uses sequential vertices. `count` is at most 64; the position decoder supports regular 16- and 32-bit floats. D3D11 indexed output and Vulkan MeshOut have been verified; full geometry views remain outstanding.

For MeshOut, add either `"meshlet":N` or `"task":N` to `mesh_draw` or `mesh_draw_export` to restrict the output to one meshlet or task group. Task groups are mapped through the TaskOut dispatch sizes. Page offsets and totals are relative to the filter; row, vertex and meshlet IDs remain absolute. The two filters are mutually exclusive, and task filtering requires available task-dispatch metadata. One Vulkan capture verifies both filters and a filtered CSV; other graphics APIs remain unverified.

After selecting `task_out` with `mesh`, `{"command":"task_payload","offset":0,"count":32}` returns task rows, dispatch dimensions, and typed payload fields from shader reflection. Values are strings, and field offsets refer to the decoded record. Vulkan post-task data uses the matching backend's scalar-packed storage layout rather than unreliable reflected array offsets. The decoder supports scalar/vector numeric types and nested structures and arrays; Vulkan matrices, bitfields and other unsupported types report errors. TaskOut bytes are never returned as floating-point positions. A Vulkan capture checks integer arrays and nested structures; other APIs remain unverified.

`{"command":"mesh_draw_export","path":"positions.csv"}` streams the complete selected draw's position rows to a new CSV file. It never overwrites an existing path and discards temporary output on failure. A D3D11 capture test exercises the CLI export and no-overwrite behavior. The export has the same stage and format limits as `mesh_draw`; it is a position export, not the complete upstream attribute export.

Mesh draw rows include reflected output attributes with their names, per-primitive flag, raw hexadecimal bytes, decoded string values when supported, and an unavailable reason. `{"command":"mesh_attributes_export","path":"attributes.csv"}` exports those attributes and individual status columns, and accepts the same optional meshlet or task filter. It creates a new file without overwriting an existing destination. Output offsets follow the active pipeline's alignment and stream rules. D3D11 position and Vulkan mesh color outputs have been verified; real per-primitive captures, other types and APIs remain unverified.

The capture snapshot lists `buffers` with session-scoped indices, upstream `resource_index`, `creation_flags`, and a decimal-string `length`. `read_buffer` requires a selected event, the buffer array `index`, an unsigned decimal-string `offset`, and an integer `length`. It returns `event_id`, `index`, `offset`, and lowercase hexadecimal bytes in `hex`. The range must lie within the buffer; length zero returns an empty result even though the upstream API uses zero to mean the rest of the buffer. Each request is limited to 65,536 bytes to bound IPC response size; page through larger buffers with successive offsets. A short or failed upstream read is an error. Generic texture raw pixels remain unavailable.

`read_texture_raw` reads bounded pages of native texture data: `{"command":"read_texture_raw","index":0,"mip":0,"slice":0,"sample":0,"offset":"0","length":256}`. The response provides `page.hex`, decimal-string `offset` and `total`, the event and subresource, the captured format name, and whether it is a whole 3D mip volume. Reads are limited to the buffer page limit; data at the end is shortened. As with raw export, 3D requires slice zero and multisampling requires an individual sample, with no casts, swizzle, channel extraction, or image-origin conversion. The matching bridge caches the complete upstream subresource in memory until another subresource, replay selection, counter replay, shader edit, or close invalidates it. Older bridges do not support this command.

`find_texture_raw` searches the native bytes in the same subresource: `{"command":"find_texture_raw","index":0,"offset":"0","hex":"00 ff 00"}`. It accepts an optional decimal-string `length`; otherwise it searches to the end. The response contains a decimal-string `offset` or null, the total byte count, event and subresource. It supports overlapping matches by starting a subsequent request at the previous offset plus one. The search streams bounded pages, includes matches crossing page boundaries, and aborts if the replay selection changes. Raw selection and memory caveats are the same as `read_texture_raw`.

`export_texture_raw` accepts `index`, `path`, and optional unsigned `mip`, `slice`, and `sample` (each defaults to zero). It exports the bytes returned by the matching RenderDoc `GetTextureData` without image conversion, channel extraction or descriptor swizzle; `channel` and type-cast arguments are rejected. For a 3D texture `slice` must be zero and the entire mip volume is returned, as reported by `whole_mip_volume`. Multisampled resources require a specific sample index; no resolved data is produced. The response includes the byte count and capture format name. The raw layout is API/format dependent and is not an image file; compressed formats remain in their captured representation. The helper uses the upstream API, which reads the complete subresource into memory. Existing destinations are never overwritten. D3D11 2D-array, 3D and individual MSAA samples and OpenGL 2D bytes have fixture coverage; other formats and drivers remain unverified.

`export_texture` optionally accepts unsigned `mip` and `slice` indices (both default to 0), plus `sample` and `channel` (unsigned indices or null). Null `sample` requests RenderDoc's resolve; null `channel` requests all components. `slice` selects the array layer or, for a 3D texture, the depth slice at the chosen mip. Indices are validated against the capture metadata instead of silently clamped. The response echoes the selection. Conversion and channel extraction follow RenderDoc's format-dependent behavior, with its default black/white mapping. Format support and conversion depend on the source texture and replay driver. The 2D array and channel paths have real D3D11 coverage; multisample and 3D paths have not been validated against real captures. An older bridge can handle the default selection but reports an error for non-default selections.

The helper and its RenderDoc core must be built from matching source revisions. `select` returning success means the upstream replay call returned without a fatal error, not that the rendered output was visually validated.

`serve` can replay a local `.rdc` on a RenderDoc remote replay server with `{"command":"open","path":"capture.rdc","remote_url":"host:port"}`. The bridge uploads a temporary copy through RenderDoc's remote protocol and uses its replay proxy; the server removes that copy when the connection closes. The original local capture remains the source for annotation sections and structured-buffer export, which uses a separate local structured-data worker without opening a local replay device; it still requires a local RenderDoc structured processor for the capture API. The optional URL must be a nonempty string. Remote target discovery and remote replay are distinct RenderDoc services and may use different ports. A Windows D3D11 loopback integration test covers upload, open and event selection; cross-machine operation and other APIs remain unverified.

`{"command":"callstack","event_id":42}` returns the event's captured CPU stack addresses as decimal strings and indicates whether a resolve database is available. Add `"resolve":true` to initialise RenderDoc's non-interactive symbol resolver and return per-frame symbols when available. Resolution can take time, depend on local or remote symbol availability, and fail; local captures use their capture file while remote sessions use the remote server's capture access. A Windows D3D11 loopback test checks captured addresses.

`target_launch` also accepts `remote_url` instead of `capture_directory` to launch through a RenderDoc remote server. `path` and `configuration.working_directory` refer to the remote filesystem; capture options, arguments and environment modifications are passed to the server, then the returned target is connected without forcing an existing client. The server must permit remote execution. Use `target_copy` to download a remote capture. Windows loopback D3D11 launch and capture have automated coverage; cross-machine and other APIs are not yet verified.

`remote_list` takes `url` and an optional remote `path`; it returns the remote home, current directory, supported remote replay drivers, local proxies, and entries with upstream flags, UTC modification time and decimal-string byte size. Preserve upstream directory error flags (0x2000, 0x4000, 0x8000). `remote_download` takes `url`, remote `path`, the nonzero decimal-string `size` from a recent listing, and an existing absolute local `capture_directory`. It creates a fresh subdirectory, downloads the file and rejects a size mismatch. Size is not a cryptographic integrity check. When the active replay session uses the exact same URL, these operations share its remote connection; otherwise they use a separate connection and can report busy when another session owns the server. Switching to another capture on the same server closes the previous replay first; if the new open fails, the previous session cannot be restored automatically. A D3D11 loopback test covers listing, transfer, content equality and size rejection; cross-machine operation remains unverified.

`gpu_list` optionally accepts a remote `url` and reports RenderDoc's GPU vendor enum, PCI device ID, driver name, display name and supported API enums. With an active replay on the same URL it reuses that connection. `open` accepts `replay_options`, for example `{"optimisation":0,"api_validation":false,"gpu_vendor":0,"gpu_device_id":0,"gpu_driver":""}`. Optimisation values are 0 none, 1 conservative, 2 balanced (default), 3 fastest; GPU vendor 0, device 0 and empty driver mean no override. The snapshot echoes the requested options; it does not report which GPU was actually selected. RenderDoc may fall back when a forced GPU is unavailable, and OpenGL does not support GPU selection. Local and remote GPU enumeration and a remote D3D11 no-optimisation open are tested; forced-GPU selection and other APIs remain unverified.

`dependencies` reports whether the active capture has embedded dependencies, whether RenderDoc is tracking pending dependencies, and their nicknames. `dependencies_save` accepts `action` (`embed` or `remove`) and an existing absolute `capture_directory`; it writes a new capture in a fresh subdirectory and returns its path. The original local file is not overwritten. Embedding replaces existing embedded data and can skip external files that are unavailable, following RenderDoc semantics. For remote replay the operation changes the session's temporary remote capture before downloading the copy; the local original remains untouched. If the local source has changed since upload, reopen it before exporting. File identity checks are metadata-based, not an atomic lock. A D3D11 fixture covers local and loopback remote embed/remove and reopening; other APIs, actual external shader-debug files and cross-machine use remain unverified.

`timeline` pages the open capture's event-ID timeline: `{"command":"timeline","start":0,"end":200,"offset":"0","limit":128}`. The optional inclusive range defaults to all IDs; offsets are decimal strings and limits are 1–128. Entries identify the snapshot action index, event ID, start/end, nesting depth, parent index, marker status, name and captured RGBA float bit patterns. Marker extents follow the upstream action hierarchy and fake-marker start rule; leaf SetMarker entries are omitted as in TimelineBar. The timeline is an event-ID axis, not a GPU-duration measurement. The GPUI view can pan, zoom, collapse markers, drag the axis or graph background to scrub actions, zoom with the wheel over either area, pan the axis or graph background with Alt-drag, and jump to displayed event highlights. Clicking the highlight band chooses the nearest pixel-history event first, otherwise the nearest resource usage, following the upstream lower-bound behavior. Complete resource usage is loaded when inspecting a resource and shown using upstream read, write, read/write, clear and barrier categories, and a pixel-history query captures all unique event IDs for its highlights; bookmarks are loaded when the capture opens and are also shown. `timeline_usage` takes a resource `index` and returns all usage records, and `timeline_history` returns the cached pixel-history query's unique events, passed_events and failed_events, plus selection metadata; an event may occur in both category lists when different fragments have different outcomes; the latter fails if no compatible history is cached. These complete lists can be large. The paginated `resource_usage` and `pixel_history` commands remain available. D3D11 local and remote-loopback tests cover the data, and a GPUI recording-transport test covers dragging and selection; real-capture UI and other APIs remain unverified or incomplete.
